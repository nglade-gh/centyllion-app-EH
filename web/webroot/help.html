1. Introduction

NetBioDyn est un environnement de modélisation et de simulation multi-agents sur grille. Il permet de décrire un modèle (des grains, des comportements, des champs), puis de le simuler pas à pas sur une grille carrée.

Le modèle décrit qui peut changer, comment, et sous quelles conditions. La simulation fait évoluer l'état de la grille en appliquant les comportements à chaque pas.

Idée directrice

Chaque case de la grille peut contenir un agent (un grain) ou être vide. À chaque pas, chaque agent examine son voisinage (les 8 cases autour de lui) et peut déclencher un comportement qui modifie sa case et/ou les cases voisines.

2. Le modèle

Le modèle regroupe trois types d'éléments :

ÉlémentRôleExemple
GrainUn type d'agent, avec une couleur, une demi-vie, une probabilité de mouvement.« Bleu », « Rouge »
ComportementUne règle de transformation : un réactif central, des voisins réactifs, des produits, et des conditions.« Bleu → Rouge »
ChampUne grandeur continue diffusant sur la grille (comme un chimique).« Nutriment »

2.1 Les grains (agents)

Un grain définit un type d'agent. Ses propriétés principales :

  • Nom : le nom affiché dans l'interface.
  • Couleur : la couleur de l'agent sur la grille.
  • Demi-vie (halfLife) : si > 0, l'agent meurt aléatoirement avec une probabilité croissante en âge. 0 = immortal.
  • Probabilité de mouvement : si > 0, l'agent peut se déplacer vers une case vide voisine.
  • Production de champ : l'agent émet un champ (par ex. un nutriment).
  • Perméabilité : l'agent freine ou laisse passer un champ.

Identifiant (ID)

Chaque grain possède un numéro d'ID unique, affiché dans la liste des grains et dans le panneau d'édition (champ « ID »). C'est cet ID qu'on utilise dans les formules, par exemple count(0) compte les voisins de l'agent d'ID 0.

2.2 Les comportements

Un comportement décrit une transformation locale. Il se compose de :

  • un réactif principal (la case centrale) ;
  • un produit principal ;
  • des réactions sur les cases voisines (réactif → produit, avec directions possibles) ;
  • des conditions : formule, probability, etc.

Exemple : prédation

Case centrale : A → vide
Voisin (B)   : B → B

Un agent A en contact avec un agent B est mangé (il disparaît). Le comportement s'applique si la case centrale contient A et si au moins un voisin contient B.

Exemple : génération spontanée

Case centrale : vide → A
Voisin (B)   : B → B

Un agent A apparaît sur une case vide si au moins un voisin B est présent. Le réactif principal none (vide) permet ce type de comportement.

Exemple : catalyse

Case centrale : A → B
Voisin (C)   : C → C

Un agent A se transforme en B en présence d'un catalyseur C.

Conditions aux limites du comportement

Chaque comportement porte ses propres parois, gauche, droite, haut et bas. Par défaut, toutes sont toriques : le comportement « voit » au-delà du bord comme si la grille s'enroulait, exactement comme avant.

Si une paroi est fermée, le comportement ne voit ni agent ni valeur de champ au-delà de cette paroi : les voisins situés derrière sont ignorés par les comptages de voisins (count(), age(n), les conditions de comptage), par les réactions et par les influences de champ. Le reste de la simulation n'est pas affecté : les autres comportements gardent leurs propres parois, et la grille elle-même ne change pas.

Cela permet par exemple de donner à un comportement un bord absorbant — une réaction qui ne se déclenche pas depuis l'autre côté de la grille — sans toucher au comportement des autres. Un comportement enregistré avec ses quatre parois toriques n'écrit rien dans le fichier .nbd2 ; dès qu'une paroi est fermée, les quatre sont écrites explicitement.

Le prédicat

La ligne Predicate (formule) définit la condition d'application du comportement. Si elle est vide, le comportement s'applique dès que le réactif principal est présent et que les réactions voisines sont satisfaites. Les variables step, x, y et les fonctions (count, field, agent, …) y sont autorisées.

Les actions

La ligne Actions définit des effets supplémentaires, exécutés après les réactions lorsque le comportement s'applique. C'est une liste d'actions séparées par des virgules :

ActionEffet
Add(id, dx, dy) Crée un agent de type id à l'offset (dx, dy) depuis la case du comportement (case cible vide uniquement).
Remove(id, dx, dy) Détruit l'agent de type id à l'offset (dx, dy).
Move(id, dx1, dy1, dx2, dy2) Déplace l'agent de type id de l'offset (dx1, dy1) à l'offset (dx2, dy2) (case cible vide ou occupée par le même type, auquel cas les deux agents échangent leurs cases).
SetField(id, dx, dy, valeur) Fixe la valeur du champ id à l'offset (dx, dy) (bornée entre 0 et 1).
AddField(id, dx, dy, delta) Ajoute delta à la valeur du champ id à l'offset (dx, dy) (résultat borné entre 0 et 1).
ClearField(id, dx, dy) Remet la valeur du champ id à l'offset (dx, dy) à 0.

Les offsets sont relatifs à la case du comportement et la grille est torique : un offset qui sort de la grille revient sur le bord opposé (comme dans field(id, dx, dy) et count). Les arguments peuvent être des expressions numériques utilisant step, x, y, count(grainId) ou field(id, dx, dy) (comptés sur l'état du début du pas, comme le prédicat).

Exemple : émission d'un signal

Predicate : count(1) > 2
Actions   : AddField(0, 0, 0, 0.2), Add(1, 0, 1)

Si un agent A compte plus de deux voisins B, il augmente le champ 0 de 0,2 dans sa case et crée un agent B au-dessus de lui.

Ordre des réactions et des actions

Au sein d'un même comportement, les réactions sont appliquées d'abord, puis les actions. Au sein des actions, l'ordre compte : les actions successives sont appliquées l'une après l'autre, chacune voyant l'effet des précédentes. Notez que count(id) est évalué sur l'état du début du pas, avant l'application des réactions et des actions.

Exemple : rôle de l'ordre des actions

Case centrale : vide ; voisin B à gauche en (-1,0)
Réaction principale : None -> A
Réaction          : B -> B (B autorisé uniquement à gauche)
Actions           : Remove(0,0,0), Remove(1,-1,0), Add(0,0,0)

Application (si le comportement est tiré au sort) :

  1. Réaction principale : centre → A ;
  2. Réaction : B à (-1,0) → B (identité) ;
  3. Remove(0,0,0) : retire l'A du centre (celui posé par la réaction principale) → case vide ;
  4. Remove(1,-1,0) : retire le B de (-1,0) → vide ;
  5. Add(0,0,0) : pose A au centre (vide) → A.

Bilan net : centre = A, B à gauche supprimé. Remove(0,0,0) n'a d'effet que parce qu'il s'exécute après la réaction principale (qui pose l'A) et avant l'Add : si l'Add avait précédé le Remove, le centre finirait vide. Si l'ordre des réactions/actions était interverti, le résultat changerait — d'où l'importance de l'ordre d'écriture dans la ligne Actions.

2.3 Les champs

Un champ est une grandeur continue définie sur toute la grille, comme la concentration d'un nutriment ou d'une molécule. À chaque pas, le champ :

  1. diffuse vers les cases voisines (selon les directions autorisées et la perméabilité des agents) ;
  2. est produit ou consommé par les agents présents ;
  3. subit une mort exponentielle (demi-vie) ;
  4. peut être transformé par une formule.

Les champs permettent de modéliser des signaux chimiques, des gradients, des ressources, etc. Les agents peuvent les percevoir via les formules.

3. La simulation

La simulation fait évoluer la grille pas à pas. À chaque pas :

  1. les agents meurent (selon leur demi-vie) ;
  2. les agents vieillissent ;
  3. chaque agent examine les comportements applicables ;
  4. les comportements retenus sont appliqués ;
  5. les champs sont mis à jour.

Le nombre de pas et la vitesse sont affichés dans la barre d'outils.

3.1 Modes de mise à jour

Deux modes sont disponibles (bouton dans la barre d'outils) :

ModeDescriptionUsage
Parallèle
défaut		 Tous les comportements sont calculés à partir de l'état du début du pas, puis appliqués simultanément. Automates cellulaires, comptages de voisins, modèles déterministes.
Séquentiel Les comportements sont appliqués immédiatement, dans un ordre aléatoire. Un comportement peut voir les changements des précédents. Modèles dépendant de l'ordre, chaînes de transformations.

Pourquoi le mode parallèle est le défaut

Dans le mode parallèle, le comptage des voisins ne dépend pas de l'ordre de mise à jour : tous les agents « voient » le même état initial. C'est le comportement attendu pour la plupart des modèles.

4. Les formules

Les formules sont des expressions mathématiques ou logiques évaluées dynamiquement. Elles sont utilisées dans deux endroits :

  • la formule d'un champ : transforme la valeur du champ à chaque pas ;
  • la formule d'un comportement : condition d'application du comportement.

4.1 Syntaxe

Les formules utilisent une syntaxe proche de l'mathématique. Priorités (de la plus forte à la plus faible) :

  1. parenthèses ( )
  2. puissance ^
  3. multiplication *, division /, modulo %
  4. addition +, soustraction -
  5. comparaisons >, >=, <, <=
  6. égalité ==, différence !=
  7. et logique &&
  8. ou logique ||
  9. ternaire condition ? siVrai : siFaux

Opérateurs unaires

  • -x : opposé
  • +x : identité
  • !x : négation logique

Littéraux

  • nombres : 1, 3.14, 0.5
  • booléens : true, false
  • constantes : pi, e

Prédicat logique

La formule d'un comportement est un prédicat logique : elle doit renvoyer true ou false. Une formule qui renvoie un nombre (par ex. sin(step)) est refusée par la validation ; si elle était quand même exécutée, le comportement ne s'appliquerait jamais.

Âge d'un agent

Dans une formule de comportement, l'âge de l'agent est disponible sous le nom step. Pour conditionner un comportement à l'âge, écrire par exemple step >= 10.

4.4 Exemples — formules de champ

La formule d'un champ est évaluée à chaque pas pour chaque case, à partir de la valeur actuelle.

Exemple 1 : décroissance

current * 0.9

Le champ perd 10 % de sa valeur à chaque pas.

Exemple 2 : oscillation

(1 + sin(step/10)) / 2

Le champ oscille entre 0 et 1 avec une période d'environ 63 pas.

Exemple 3 : gradient spatial

x / 100

Le champ croît linéairement avec la coordonnée x.

Exemple 4 : diffusion conditionnelle

current > 0.1 ? current * 0.8 : 0

Au-dessus de 0.1, le champ décroît ; en dessous, il s'annule.

Exemple 5 : influence du voisinage

count(0) > 2 ? current * 0.95 : current

Le champ décroît seulement quand il y a plus de 2 agents de type 0 autour de la case.

4.5 Exemples — formules de comportement

La formule d'un comportement est évaluée pour chaque agent susceptible de l'appliquer.

Exemple 1 : condition sur l'âge

step >= 10

Le comportement ne s'applique que si l'agent a au moins 10 pas.

Exemple 2 : comptage de voisins

count(0) >= 3 && count(0) < 5

Le comportement s'applique s'il y a entre 3 et 4 voisins de type 0.

Exemple 3 : combinaison de conditions

step > 10 && (count(1) > 3 || count(2) == 5)

Le comportement s'applique si l'agent a plus de 10 pas et s'il y a plus de 3 voisins de type 1 ou exactement 5 de type 2.

Exemple 4 : condition sur un champ

field(0) > 0.05

Le comportement s'applique si le champ 0 est supérieur à 0.05 sur la case.

Exemple 5 : condition sur un champ voisin

count(0) > 3 && field(1, 1, 0) < 0.5

Le comportement s'applique s'il y a plus de 3 voisins de type 0 et que la valeur du champ 1 sur la case à l'est est inférieure à 0.5.

Exemple 6 : condition de position

x == 0 || x == 99

Le comportement s'applique uniquement sur les bords gauche et droit de la grille.

5. Exemples complets

Automate cellulaire : jeu de la vie simplifié

Grains : 0 = mort, 1 = vivant.

Comportement "Naissance" : vide → 1, formule : count(1) == 3
Comportement "Mort"     : 1 → vide, formule : count(1) < 2 || count(1) > 3
Comportement "Survie"   : 1 → 1,   formule : count(1) == 2 || count(1) == 3

Prédation avec seuil de population

Grains : 0 = proie, 1 = prédateur.

Comportement "Prédation" : 0 → vide, voisin (1) : 1 → 1, formule : count(1) >= 1
Comportement "Reproduction" : 0 → 0, voisin (1) : 1 → 1, formule : count(0) > 5

Chimiotaxie

Grains : 0 = bactérie ; Champ : 0 = nutriment.

Comportement "Avancer vers le nutriment" : 0 → 0, avec seuil de champ 0 (valeur > 0.1)

Conseil

Commencez par un modèle simple (quelques grains, un ou deux comportements), vérifiez le comportement pas à pas, puis ajoutez progressivement les conditions et les champs.

6. Galerie de modèles

La galerie rassemble des modèles prêts à ouvrir, présentés en miniatures : une image, le titre du modèle affiché dessus, et une courte description en dessous. Un clic sur une miniature propose de charger le modèle dans l'application.

6.1 Deux galeries

La galerie distribuée fait partie du logiciel : elle est identique pour tous et ne peut pas être modifiée depuis l'application. La galerie personnelle contient les modèles que vous ajoutez ; elle est stockée dans les données de votre navigateur, sur ce poste uniquement.

Vos ajouts ne sont donc ni publiés, ni visibles des autres utilisateurs, et ils ne suivent pas d'un ordinateur à l'autre. Ils disparaissent si vous effacez les données du navigateur.

6.2 Ajouter un modèle

Le bouton Ajouter un modèle demande un fichier de sauvegarde (.nbd2 ou .netbiodyn), puis un titre — prérempli avec le nom du modèle — et une description. Le nom, la description et l'image peuvent être repris du fichier ; ils restent modifiables ensuite. Sans image, une vignette de l'état initial de la simulation est générée.

6.3 Conserver et transférer

Exporter ma galerie télécharge un fichier ma-galerie.json autonome, qui contient vos modèles. C'est votre sauvegarde, et le seul moyen de retrouver votre galerie sur un autre poste ou après un nettoyage du navigateur : Importer ma galerie la reconstitue. La galerie distribuée n'est pas concernée par ces deux boutons.

6.4 Description du modèle et description de galerie

Le bouton Infos modèle, au-dessus des Agents, édite le nom et la description du modèle : cette description est enregistrée dans le fichier .nbd2. La description saisie dans la galerie est une présentation destinée aux miniatures ; elle n'est jamais écrite dans le fichier de sauvegarde.

7. Commandes de grille

Dans les formules d'actions d'un modificateur, les commandes de grille agissent sur la sélection courante et sur la mémoire (presse-papiers) de la vue de simulation, jamais sur une cellule. Elles sont exécutées à la fin du pas, dans l'ordre de la formule.

Trois d'entre elles sont faciles à confondre :

  • EraseSelection() — détruit les agents de la zone sélectionnée, puis désélectionne. La grille est modifiée.
  • FlushSelection() — vide la mémoire : la sélection copiée ou coupée est oubliée, il n'y a plus rien à coller. La grille n'est pas modifiée.
  • Unselect() — lâche le rectangle de sélection, sans toucher ni à la grille ni à la mémoire.

Copy() et Cut() remplissent la mémoire, Paste(x, y, overwrite) la colle, PasteAndFlush(x, y, overwrite) colle puis vide la mémoire. Select(x1, y1, x2, y2) définit la zone, Rotate(N), FlipX() et FlipY() transforment la mémoire, Show(id) et Hide(id) changent la visibilité des agents.

7.1 Les interrupteurs de la barre d'édition

Deux commandes agissent sur les interrupteurs « Torique ? » et « Écraser ? » de la barre d'édition, exactement comme un clic sur l'interrupteur : le widget change d'état, et le choix vaut pour les collages suivants.

  • AllowToricSelection(true) / AllowToricSelection(false) — active ou désactive « Torique ? » : un collage qui déborde de la grille se poursuit du côté opposé.
  • AllowOverwriting(true) / AllowOverwriting(false) — active ou désactive « Écraser ? » : un collage remplace les agents visibles au lieu de se contenter des cellules vides.

Ce sont des actions, pas des tests : elles s'écrivent dans la formule d'actions, séparées par des virgules, et l'argument est le littéral true ou false (jamais une expression ni 0/1).

7.2 Les tests d'état, réservés à la condition

Cinq fonctions, toutes écrites avec une majuscule, permettent d'interroger l'état de la simulation et de la vue depuis une formule. Ce sont des tests : ils renvoient 1 (vrai) ou 0 (faux) et s'écrivent uniquement dans la condition d'un modificateur.

  • IsBehaviourActive(id) — 1 quand le comportement id est actif, 0 quand il est inactif.
  • IsModifierActive(id) — 1 quand le modificateur id est actif, 0 quand il est inactif.
  • IsToricSelectionOn() — 1 quand « Torique ? » est actif, 0 sinon.
  • IsOverwritingOn() — 1 quand « Écraser ? » est actif, 0 sinon.
  • IsVisible(id) — 1 quand les agents de type id sont visibles dans la vue, 0 quand ils sont masqués (par Hide(id) ou par l'interrupteur de l'explorateur).
Condition : IsVisible(0) && IsToricSelectionOn()
Actions   : Hide(0), AllowOverwriting(true)

La négation s'écrit avec l'opérateur ! : !IsBehaviourActive(0). Il n'existe pas de test « inactif » séparé. Une formule d'actions qui contient un test (IsBehaviourActive(0), IsVisible(0)…) est refusée, et la condition d'un comportement aussi : ces tests décrivent la simulation entière et la vue, pas la cellule d'un comportement.

8. Méta-actions de la boucle de simulation

Dans la formule d'actions d'un modificateur — le seul endroit où les méta-actions sont admises — cinq actions pilotent la boucle de course et non la grille : elles arrêtent la course, la suspendent un moment, exécutent un nombre de pas donné ou rembobinent la simulation à son état initial. Comme les autres méta-actions, une demande est appliquée à la fin du pas qui l'émet : le pas en cours est terminé, puis la boucle obéit.

ActionEffet sur la boucle
Pause() Arrête la course à la fin du pas courant, définitivement. C'est le bouton Stop, écrit dans une formule. Un bandeau d'avertissement apparaît alors au-dessus de la simulation : la course ne repart que par le bouton Run ou le pas à pas.
Pause(t) Pause minutée : gèle la course pendant t secondes réelles (t > 0, littéral ou expression, par exemple 2.5), puis la relance seule. Aucun pas n'est exécuté pendant la pause : la grille et le compteur de pas ne bougent pas. Le bandeau d'avertissement indique la durée et disparaît à la reprise. t <= 0 est refusé à l'écriture quand la valeur est constante, et ignoré à l'exécution sinon (comme N <= 0 pour RunNStep).
RunOneStep() Exécute exactement un pas de plus, puis se remet en pause. C'est le bouton « pas à pas », écrit dans une formule : la course avance d'un pas et s'arrête.
RunNStep(N) Exécute N pas de plus (N entier, arrondi au plus proche), puis se met en pause. N <= 0 est ignoré : aucune étape n'est demandée et la course n'est pas interrompue.
Rewind() Revient à l'état initial sans relancer : la grille, l'état d'activation des comportements et des modificateurs et le compteur de pas repartent de zéro, et la course reste en pause. C'est le bouton de rembobinage.
Restart() Revient à l'état initial et relance la course : rembobinage suivi du bouton Run.

Une septième méta-action ne touche ni la boucle ni la grille : Capture() demande une image JPEG de la vue de simulation, prise à la fin du même pas. Elle est décrite en détail au §9.

Deux exemples, à écrire dans la formule d'actions d'un modificateur :

Condition : step == 20
Actions   : RunNStep(5)
# au pas 20, la course exécute cinq pas de plus puis s'arrête au pas 25

Condition : step == 100
Actions   : Rewind()
# au pas 100, la simulation revient à son état initial et reste en pause

Si plusieurs demandes tombent dans le même pas, l'ordre d'application est Restart, Rewind, Pause/Pause(t), RunOneStep/RunNStep : la dernière de cette liste l'emporte. Les pas demandés par deux formules s'additionnent, et un Pause() annule ceux qui restent à exécuter.

Condition : step == 5
Actions   : Pause(2)
# au pas 5, la course se gèle environ deux secondes, puis repart seule

8.0 Pause minutée : confort d'affichage, pas horloge de modèle

Pause(t) ne change jamais la trajectoire de la simulation : aucun pas n'est exécuté pendant la pause, la grille reste exactement dans l'état où le pas déclencheur l'a laissée. La suite des états est donc reproductible dès que le déclencheur l'est (step == 10, un comptage de voisins, une valeur de champ) : on retrouve les mêmes états, au même numéro de pas, à chaque exécution.

Seule la durée de la pause dépend de l'horloge de la machine : elle vaut au moins t secondes, et davantage si l'onglet passe en arrière-plan, car c'est une image d'animation qui constate la fin de l'échéance et que le navigateur les raréfie alors. Ne pas s'en servir comme d'une horloge de modèle (pour dater un événement ou synchroniser deux simulations) : pour cela, il n'y a que le compteur de pas.

8.1 Règle de casse des noms

Les méta-fonctions (actions d'un modificateur) et les méta-tests (tests d'état de la condition) commencent par une majuscule : Pause, RunOneStep, RunNStep, Rewind, Restart, AddRect, IsVisible… Les fonctions de formule et les prédicats restent en minuscules : abs, min, max, sin, cos, count, field, age, agent, ainsi que les variables step, x, y, z et current. Un nom de formule est sensible à la casse : isvisible(0) n'existe pas et la formule est refusée.

8.2 pause() est obsolète

La méta-action pause(), écrite en minuscules, reste acceptée pour les modèles déjà enregistrés : ils continuent de se charger et de se comporter à l'identique. Elle est en revanche obsolète, et c'est la seule méta-fonction qui ne respectait pas la règle de casse. Écrivez Pause() : c'est ce nom qu'affiche l'aide contextuelle, et pause() n'est conservé que pour la compatibilité.

9. Captures et dossier de travail

La méta-action Capture() demande une image JPEG (qualité 0,92) de la vue de simulation. Elle s'écrit sans argument, en majuscule, dans la formule d'actions d'un modificateur : c'est une méta-action, une formule d'actions de comportement la refuse comme toutes les autres.

Condition : step == 20
Actions   : Capture()
# au pas 20, l'image de la vue de simulation est enregistrée

9.1 Quand l'image est prise

Comme toute méta-action, Capture() s'exécute une fois par pas, après les comportements, à la fin du pas dont la condition est vraie. L'image est prise juste après le rendu complet de ce pas, avant que le pas suivant ne repeigne le canevas : elle montre exactement l'état obtenu par le pas déclencheur, avec la grille, les champs et la sélection tels qu'ils sont affichés.

Le cœur de la simulation ne dessine rien : il ne fait qu'incrémenter un compteur (Simulator.captureRequestCount, construit sur le modèle de modifierPauseCount). La vue lit ce compteur après le pas (consumeCaptureRequest()), encode le canevas puis remet le compteur à zéro : tout le rendu reste dans la vue.

9.2 Nom du fichier

Le fichier s'appelle NOM_MODELE__PAS.jpg : le nom du modèle, deux soulignés, le numéro de pas.

GoL_Modifiers__12.jpg

Le nom du modèle est nettoyé pour le système de fichiers : les caractères /, \, :, *, ?, ", <, > et | deviennent des soulignés, les espaces et les points en début et en fin sont retirés, et la longueur est bornée à 64 caractères. Les accents sont conservés. Un nom inutilisable (vide, composé d'espaces, . ou ..) donne le repli explicite model : l'image s'appelle alors model__12.jpg. Un nom de périphérique Windows (CON, NUL, COM1…) reçoit un souligné en tête.

Le numéro est celui du pas de l'image, c'est-à-dire le compteur affiché une fois le pas exécuté : une condition step == 5 déclenche la capture à la fin de ce pas, et l'image — qui montre l'état obtenu par ce pas — porte le numéro 6.

9.3 Dossier de travail

Le bouton maison — l'icône fa-home pleine, dans la rangée du bouton Informations sur le modèle, sous la barre du haut — ouvre le contrôle Dossier de travail. Son infobulle (attribut title et aria-label) porte l'état : « Dossier de travail — Défini », « Dossier de travail — Non défini » ou « Dossier de travail — Permission à renouveler ». Il laisse choisir un dossier du disque en lecture-écriture, redonner la permission ou oublier le dossier ; le sélecteur s'ouvre dans le dossier de travail courant. Son apparence dit l'état : magenta plein (#d24193, la couleur danger du thème) quand aucun dossier n'est défini, bleu plein (#9595f8, la couleur primaire des boutons + du modèle) quand le dossier est défini et accessible, même bleu atténué quand la permission doit être renouvelée.

Les captures sont alors écrites dans un dossier captures, puis dans un sous-dossier portant le nom du modèle, les deux créés au besoin :

Mes simulations/
  └── captures/
        └── GoL_Modifiers/
              ├── GoL_Modifiers__12.jpg
              └── GoL_Modifiers__13.jpg

Le dossier est mémorisé à part de tout le reste : son handle vit dans sa propre base IndexedDB — centyllion-home, version 1, magasin handles, clé home — qui ne partage rien avec la galerie (centyllion-gallery) ni avec les handles du dialogue d'enregistrement (centyllion-files). localStorage ne garde que deux chaînes : le nom à afficher et le mode de repli. L'ancienne clé workFolder de centyllion-files n'est ni lue ni migrée : elle est simplement supprimée si elle existe, et le dossier est choisi à nouveau.

Aucune image ne passe par le stockage du navigateur : rien dans IndexedDB, localStorage, sessionStorage ni Cache Storage. La capture est encodée en mémoire (un Blob), puis écrite dans le dossier ou téléchargée — elle n'a pas d'autre destination. La base centyllion-home refuse d'ailleurs tout ce qui n'est pas un handle de dossier.

La boîte de dialogue donne l'état du dossier : non défini, défini ou permission à renouveler. Un navigateur redemande parfois la permission après un redémarrage : le bouton Reconnecter la rend d'un clic (queryPermission puis requestPermission), sans choisir le dossier une seconde fois.

Sans dossier de travail, si la permission n'est pas accordée, ou si l'écriture échoue, l'image est téléchargée (Blob + attribut download). Un message dit toujours laquelle des deux voies a été suivie, et pourquoi : une capture ne bascule jamais silencieusement en téléchargement, et showSaveFilePicker n'est jamais la seule voie.

Sur un navigateur sans File System Access, le bouton maison reste présent, en magenta plein : son infobulle dit « Dossier de travail — Non défini » et il ouvre la même boîte de dialogue, qui explique que les captures partiront en téléchargement, un fichier par pas. Aucune fonctionnalité de capture n'est réservée à Chrome ou à Edge.

Débit : chaque capture encode le canevas en JPEG et écrit un fichier. À 50 pas par seconde, un Capture() sans condition produit 50 fichiers par seconde : préférez un déclencheur rare (step % 10 == 0, un comptage de voisins, une valeur de champ), ou une pause avant la capture.
